# Grok device OAuth browser-verification hosts

Researched 2026-11-07 using anonymous public primary sources only. Target file absence was checked before creation.

## Conclusion and certainty

**An exact production device-verification hostname allowlist was not established.** No device grant was requested, so no real `verification_uri` or `verification_uri_complete` was observed. Neither the issuer host nor an unrelated consent-page origin proves the device-verification host. The defensible confirmed-device-host set from this research is **empty**, not `*.x.ai`.

- **High certainty — issuer/API host:** [xAI OIDC discovery](https://auth.x.ai/.well-known/openid-configuration) returns `issuer: https://auth.x.ai` and device-authorization/token/authorization endpoints on that host, but **no browser verification URI**. These endpoint URLs were read as metadata, not invoked. The [official enterprise network table](https://docs.x.ai/build/enterprise) calls `auth.x.ai` “OAuth2/OIDC authentication”; its device-code section says the CLI prints a URL, without naming that URL's host. This does not establish `auth.x.ai` as the device-verification host.
- **High certainty — production consent UI origin, not device-specific proof:** [official configuration, lines 124–126](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-login/src/config.rs#L124-L126) separates issuer `https://auth.x.ai` from production accounts-app origin `https://accounts.x.ai`. Its [frozen loopback contract, lines 614–619](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-login/src/config.rs#L614-L619) explicitly identifies `accounts.x.ai` as the consent-page origin. **Candidate only for device verification; not confirmed.**
- **High certainty — official device client does not pin a host:** [device-code source, lines 157–164](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-login/src/device_code.rs#L157-L164) copies both URI fields from the response; [lines 317–320](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-login/src/device_code.rs#L317-L320) select the complete URI when present. Its [validator, lines 474–486](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-login/src/device_code.rs#L474-L486), checks scheme, not an exact production hostname. [Test fixtures](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-login/src/device_code.rs#L750-L755) use `example.test`, not production evidence.

## Feature-branch policy and remaining release check

The feature branch allows only `accounts.x.ai`, because the pinned official source above establishes it as xAI's accounts/consent origin. **This is a reviewed first-party-origin permission, not a claim that a real device response was observed.** The SDK-selected verification URL must independently pass HTTPS, exact hostname, no userinfo and no nonstandard port before the panel displays, copies or opens it. `auth.x.ai`, other subdomains and response-provided unknown hosts remain blocked. Synthetic test paths on the permitted origin verify this policy only; they do not establish the production device URL or a completed login.

The official adapter exposes only its selected verification URL; the plugin does not reimplement OAuth to inspect both original URI fields. A separately authorized real device-flow check must confirm the returned origin and full panel flow before claiming end-to-end support. If the returned origin differs, stop and review new primary evidence rather than relaxing the allowlist automatically. A stricter release gate may keep login disabled altogether until that observation; this branch is for offline integration validation, not proof of that release gate.

## Method limits

Search results were followed to official docs, anonymous OIDC metadata and pinned official source. `web_fetch` failed at its service endpoint; fallback was Python stdlib HTTP GET, with redirects disabled, no cookies/credentials, and no execution of downloaded code. Accounts-host OIDC discovery and auth-host OAuth authorization-server discovery returned 404. No grant, device/code, token, login, inference endpoint, account data, installation, git operation, or test was used. These sources do not establish the actual device-verification host; an explicit official device-URL statement or a separately authorized observation would be needed to close that gap.
